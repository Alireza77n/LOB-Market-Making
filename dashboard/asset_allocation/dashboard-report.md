
# Shifu Trading Engine Replay

An event-driven Streamlit application for replaying an out-of-sample trading run built from DeepLOB signals and a Deep Learning Sharpe (DLS) portfolio allocation layer.

This project is **not** a static CSV dashboard. It rebuilds the trading process as a replayable state machine:

```text
DeepLOB probabilities
    -> signal score and confidence
    -> entry / quality filters
    -> DLS target weights
    -> submitted orders
    -> executed trades
    -> end-of-day holdings
    -> portfolio and model comparison metrics
```

The app is designed for inspecting *why* a trading decision happened on each out-of-sample day, not only for viewing final performance.

---

## 1. Main capabilities

- Interactive day-by-day replay of the trading engine.
- Manual replay with previous / next buttons and a day slider.
- Optional auto-play with safe refresh intervals.
- Fast playback mode that skips heavy plots while the replay is running.
- Same-day DeepLOB three-class signal inspection: `P(down)`, `P(flat)`, `P(up)`.
- Asset-level decision book linking `P(down)`, `P(flat)`, `P(up)`, filters, previous weights, DLS target weights, submitted orders, filled executions, and final EOD holdings.
- Execution reconciliation table showing submitted buy/sell percentages versus filled buy/sell percentages for every asset.
- Daily comparison between:
  - `Base DeepLOB`
  - `DeepLOB + DLS`
- Final model comparison cockpit with return, Sharpe, drawdown, cost, and order divergence.
- Training diagnostics for DLS training history and optional seed-search analysis.

## 6. How the app reconstructs the replay state

The app loads the CSVs, normalizes important numeric columns, and creates a unified daily replay table called `summary`.

At every replay step, the app builds an `EngineState` object:

```text
EngineState = {
    day,
    index,
    row,
    raw DeepLOB signals,
    DLS weight-step rows,
    DLS filled trades,
    DLS holdings,
    DLS weight/debug row,
    DLS submitted orders,
    Base DeepLOB submitted orders
}
```

This lets every dashboard view reference the same current replay day.

### Important derived metrics

| Metric                      | Formula / source                                                          | Meaning                                                                     |
| --------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `day_index`               | Numeric part of`trade_day_id`                                           | Used to sort replay days chronologically.                                   |
| `engine_target_gross`     | `target_gross`, fallback to sum of target weights, fallback to `0.95` | Target gross exposure used by the DLS engine.                               |
| `dls_equity_proxy`        | `eod_market_value / engine_target_gross`                                | Reconstructed DLS portfolio equity proxy.                                   |
| `dls_cash_proxy`          | `dls_equity_proxy - eod_market_value`                                   | Implied cash proxy under the reconstructed DLS equity assumption.           |
| `dls_return_proxy_%`      | `(dls_equity_proxy / first_valid_dls_equity_proxy - 1) * 100`           | Reconstructed cumulative DLS return path.                                   |
| `base_return_%`           | `(base_portfolio_value / first_base_portfolio_value - 1) * 100`         | Base DeepLOB cumulative return path.                                        |
| `dls_daily_return_%`      | `pct_change(dls_equity_proxy) * 100`                                    | DLS same-day return proxy.                                                  |
| `base_daily_return_%`     | `pct_change(base_portfolio_value) * 100`                                | Base DeepLOB same-day return.                                               |
| `executed_total_turnover` | DLS filled buy + sell turnover                                            | Total DLS traded notional for the replay day.                               |
| `base_total_turnover_day` | `base_buy_turnover + base_sell_turnover`                                | Total Base DeepLOB traded notional for the replay day.                      |
| `dls_cum_turnover`        | Cumulative sum of DLS turnover                                            | Cumulative DLS trading intensity.                                           |
| `base_cum_turnover`       | Cumulative sum of base turnover                                           | Cumulative Base DeepLOB trading intensity.                                  |
| `dls_cum_cost`            | Cumulative sum of DLS costs                                               | Cumulative DLS trading cost.                                                |
| `base_cum_cost`           | Cumulative sum of base costs                                              | Cumulative Base DeepLOB trading cost.                                       |
| `quality_pass_rate`       | `quality_candidates / entry_candidates`                                 | Fraction of entry candidates that pass quality filtering.                   |
| `target_utilization`      | `target_names / quality_candidates`                                     | Fraction of quality-passed candidates that receive positive target weights. |
| `execution_rate`          | `executed_assets / target_names`                                        | Fraction of targeted names that actually trade.                             |

### Trading Pipeline Stage Line

The stage line is a compact replay of the full trading engine for the selected out-of-sample day. It should be read from left to right as a state transition, not as a set of independent performance metrics.

```text
Signal Bus
    -> Entry Mask
    -> Quality Filter
    -> DLS Optimizer
    -> Execution
    -> Portfolio State
```

Each stage answers one question:

```text
What did DeepLOB predict?
    -> Which assets were tradable/eligible?
    -> Which signals were strong enough?
    -> What portfolio weights did DLS want?
    -> What orders were actually executed?
    -> What did the portfolio hold at the end of the day?
```

The notebook uses a shifted, no-lookahead convention for the DLS pipeline. A DeepLOB signal is generated on a signal/observation day `t`, using information available up to that day. The resulting decision is applied to the next trade day `t+1`. This is why the dashboard shows both a `signal_day_id` and a `trade_day_id`. The stage line therefore represents the journey from a prior-day model signal into a next-day trading decision.

---

#### 1. `Signal Bus`

`Signal Bus` is the raw DeepLOB prediction layer.

At this stage, the model has not yet made a portfolio allocation. It has only produced directional probabilities for each asset:

```text
P(down), P(flat), P(up)
```

These probabilities come from the three-class DeepLOB output. They describe whether the model expects the asset to move down, remain flat, or move up. The notebook then derives two important signal features from these probabilities:

```text
signal_score = P(up) - P(down)

confidence = |signal_score| × (1 - P(flat))
```

The interpretation is:

* `P(up)` measures bullish probability.
* `P(down)` measures bearish probability.
* `P(flat)` measures uncertainty or no-direction probability.
* `signal_score` measures directional strength.
* `confidence` rewards signals that are both directional and not too flat.

The number shown in this stage represents how many raw DeepLOB buy-side signals are available on the current replay day, while the subtitle shows the broader raw signal universe. This is the widest part of the funnel. It tells you how much signal supply the model produced before any portfolio or execution logic was applied.

A high `Signal Bus` value means DeepLOB was broadly bullish across many assets. A low value means the raw model was more selective or that fewer assets had usable bullish predictions.

This stage does **not** mean those assets will be bought. It only means the model produced raw signal candidates.

---

#### 2. `Entry Mask`

`Entry Mask` is the first execution-aware gate.

The notebook separates prediction from tradability. Even if DeepLOB produces a strong signal, the asset still needs to be eligible for trading on the actual trade day. The entry mask represents this tradability/eligibility condition for the execution day.

This stage is important because the DLS model must not use future information to decide which assets are tradable. The notebook explicitly keeps the entry mask tied to information available before the trade is executed. Future return information can be used later for labels or loss validation, but not to decide whether an asset is allowed into the optimizer.

The number in this box shows how many assets passed the initial entry condition and can move forward into the DLS allocation pipeline.

Interpretation:

* If `Signal Bus` is high but `Entry Mask` is much lower, many raw signals were not tradable or not eligible.
* If `Signal Bus` and `Entry Mask` are close, most raw signal candidates were eligible for the next step.
* Passing the entry mask still does not guarantee a trade; it only means the asset is allowed to be considered.

---

#### 3. `Quality Filter`

`Quality Filter` is the signal-strength gate.

After assets pass the entry mask, the notebook applies a DeepLOB-derived quality filter before converting signals into DLS orders. The filter is based on the signal features:

```text
signal_score = P(up) - P(down)

confidence = |signal_score| × (1 - P(flat))
```

An asset is kept only if its confidence and signal score are strong enough according to the configured thresholds. In practical terms, this stage asks:

```text
Is this signal strong enough to justify portfolio allocation and transaction costs?
```

This matters because weak signals can create unnecessary turnover. A model may produce many raw predictions, but trading all of them can increase costs and reduce net performance. The quality filter is therefore a transaction-cost-aware defense against noisy trades.

The stage line usually shows:

```text
quality_candidates
pass rate = quality_candidates / entry_candidates
```

Interpretation:

* A high pass rate means most eligible signals were strong enough.
* A low pass rate means the engine rejected many weak or uncertain signals.
* If the filter becomes too strict and too few names survive, the notebook can fall back to the top-confidence tradable names so that the portfolio remains investable and minimum-holding constraints can still be respected.

This stage explains why a stock with a positive `P(up)` may still receive no DLS allocation.

---

#### 4. `DLS Optimizer`

`DLS Optimizer` is the portfolio construction stage.

After the entry and quality filters, the DLS layer converts the surviving DeepLOB signal features into target portfolio weights. In the notebook, the DLS model is a long-only allocation layer. Its output is post-processed into executable target weights.

Conceptually, this stage converts:

```text
filtered DeepLOB signal features
    -> target portfolio weights W_t
```

The target weight means:

```text
W_{t,i} = desired portfolio fraction allocated to asset i
```

Interpretation:

* If `target_weight > 0`, the DLS optimizer wants the portfolio to hold that asset.
* If `target_weight = 0`, the optimizer does not want exposure to that asset.
* Since this implementation is long-only, final executable weights are normally non-negative.
* The optimizer does not simply buy every positive DeepLOB signal. It ranks, filters, and allocates across assets under portfolio-level constraints.

The number shown in this stage is the number of assets with positive target weights, often called `target_names`.

This stage is where the system moves from prediction to allocation. It answers:

```text
Which filtered signals became actual portfolio targets?
```

A useful way to read this stage is to compare it with the previous one:

```text
quality_candidates -> target_names
```

If many assets pass the quality filter but only a smaller number receive target weights, the optimizer is concentrating capital into the most attractive subset.

---

#### 5. `Execution`

`Execution` is the trading-action stage.

The notebook does not stop at target weights. It compares the current portfolio weights with the DLS target weights, then submits buy or sell orders to move the portfolio toward the desired allocation.

The key logic is:

```text
target weight - current weight = rebalance gap
```

Examples:

```text
current weight = 2%, target weight = 5%
-> buy approximately 3% more exposure

current weight = 6%, target weight = 1%
-> sell approximately 5% exposure

current weight > 0%, target weight = 0%
-> reduce or close the position
```

Execution is also constrained by realistic trading mechanics:

* available cash
* cash buffer
* lot size
* sellable shares
* transaction costs
* commissions
* stamp duty
* locked shares
* execution price availability

The notebook uses open-based execution logic for the DLS strategy. Sells use the configured sell mode, which is set to open by default in this version, and rebalance sizing uses the decision/open price. Same-day close is reserved for end-of-day valuation and logging, not for same-day execution sizing.

This stage reports how many assets were actually executed, separated into buys and sells.

Important distinction:

```text
submitted order ≠ filled execution
```

A submitted order percentage says what the strategy tried to buy or sell. A filled execution shows what actually happened after applying price, cash, lot-size, sellability, and cost constraints.

This stage answers:

```text
What did the strategy actually trade today?
```

---

#### 6. `Portfolio State`

`Portfolio State` is the end-of-day result of the trading step.

After the execution engine updates cash and holdings, the portfolio is valued using end-of-day prices. The dashboard then reports the final holdings and concentration state for the selected replay day.

This stage is built from the DLS holding snapshot and represents the final portfolio after:

```text
signals
    -> filters
    -> target weights
    -> submitted orders
    -> filled executions
    -> EOD valuation
```

The main value is the number of active end-of-day holdings. The subtitle usually reports top-10 concentration, which shows how much of the portfolio is held in the ten largest positions.

Interpretation:

* More holdings usually means broader diversification.
* Fewer holdings means a more concentrated portfolio.
* A high top-10 weight means exposure is concentrated in the largest positions.
* A lower top-10 weight means exposure is more evenly distributed.

This stage answers:

```text
What does the portfolio look like after the day’s trading decisions?
```

It is the final state of the replay step, not just a chart of orders.

---

### How to read the full stage line

The stage line should be interpreted as a decision funnel:

```text
Raw DeepLOB signal universe
    -> entry-tradable universe
    -> high-quality signal candidates
    -> DLS target portfolio
    -> filled trades
    -> final EOD holdings
```

A useful diagnostic reading is:

| Transition                          | What it tells you                                                   |
| ----------------------------------- | ------------------------------------------------------------------- |
| `Signal Bus -> Entry Mask`        | How many raw signals were actually eligible for execution.          |
| `Entry Mask -> Quality Filter`    | How much noisy or weak signal activity was removed.                 |
| `Quality Filter -> DLS Optimizer` | How selective the portfolio optimizer was after filtering.          |
| `DLS Optimizer -> Execution`      | Whether target weights translated into actual trades.               |
| `Execution -> Portfolio State`    | How the day’s trades changed the final holdings and concentration. |

For example:

* If `Signal Bus` is high but `Quality Filter` is low, DeepLOB produced many raw signals, but most were not strong enough.
* If `Quality Filter` is high but `DLS Optimizer` is low, the optimizer chose to concentrate capital in only a subset of good signals.
* If `DLS Optimizer` is high but `Execution` is low, the portfolio may already be close to target weights, or execution constraints may have prevented many trades.
* If `Execution` is high but `Portfolio State` changes only slightly, trades may have been small rebalancing adjustments rather than large position changes.

In short, the stage line is a compressed explanation of the complete DeepLOB + DLS trading path. It shows how the notebook moves from model probabilities to a filtered allocation, then from target weights to real trades, and finally from trades to the end-of-day portfolio.

### Main table: `Combined Decision Book`

This table is the main asset-level explanation table in the Decision Inspector. It combines the DeepLOB signal, DLS filtering result, portfolio-weight transition, submitted order, filled execution, and final holding state into one row per asset.

The purpose of this table is to make the full decision chain readable without switching between multiple CSV files. For each asset, you can see:

```text
DeepLOB probabilities
    -> DLS signal score / confidence
    -> entry and quality filter status
    -> previous weight
    -> DLS predicted target weight
    -> post-trade weight
    -> final EOD weight
    -> submitted buy/sell %
    -> filled buy/sell %
    -> filled shares and turnover
```

The most important distinction is:

- `DLS submitted buy %` / `DLS submitted sell %` describe the order that the DLS strategy submitted.
- `Filled buy %` / `Filled sell %` describe what was actually filled according to the trade-audit file.
- `Previous weight`, `DLS predicted target weight`, `Post-trade weight`, and `Final EOD weight` explain how the asset moved inside the portfolio.

| Column                          | Meaning                                                                                                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Asset`                       | Asset identifier.                                                                                                                                   |
| `Engine action`               | Final action assigned by the replay engine for the current day:`BUY`, `SELL`, or `HOLD`.                                                      |
| `DeepLOB P(down)`             | DeepLOB probability that the asset will move downward.                                                                                              |
| `DeepLOB P(flat)`             | DeepLOB probability that the asset will remain approximately flat or have no meaningful directional move.                                           |
| `DeepLOB P(up)`               | DeepLOB probability that the asset will move upward.                                                                                                |
| `Signal score`                | DLS signal score used by the allocation layer. It summarizes directional signal information used downstream by the portfolio engine.                |
| `Confidence`                  | Confidence or quality score used to rank/filter assets before allocation.                                                                           |

| `Filled sell shares`          | Number of shares actually sold by DLS for this asset.                                                                                               |

| `Base submitted buy %`        | Buy percentage submitted by the Base DeepLOB strategy for the same asset and replay day.                                                            |
| `Base submitted sell %`       | Sell percentage submitted by the Base DeepLOB strategy for the same asset and replay day.                                                           |

#### How to read this table

A useful reading sequence is:

1. Start from the three DeepLOB probabilities: `DeepLOB P(down)`, `DeepLOB P(flat)`, and `DeepLOB P(up)`.
2. Check whether the asset passed `Entry passed` and `Quality passed`.
3. Compare `Previous weight` with `DLS predicted target weight`.
4. Check whether the order was submitted through `DLS submitted buy %` or `DLS submitted sell %`.
5. Check whether that order was actually filled through `Filled buy %` or `Filled sell %`.
6. Confirm the final portfolio exposure using `Final EOD weight`.

Example interpretation:

- If `DeepLOB P(up)` is high, `Quality passed` is true, and `DLS predicted target weight` is greater than `Previous weight`, the DLS engine is trying to increase exposure to that asset.
- If `DLS submitted buy %` is positive but `Filled buy %` is zero, an order was submitted but no filled buy execution is recorded in the trade-audit table.
- If `DLS predicted target weight` is positive but `Final EOD weight` remains low, the optimizer wanted exposure but the actual portfolio state did not fully reach that target.

#### How to read this table

This table should be read as an execution audit:

1. Use `DeepLOB P(down)`, `DeepLOB P(flat)`, and `DeepLOB P(up)` to understand the same-day model signal.
2. Use `Previous weight` and `DLS predicted target weight` to see what the DLS optimizer wanted to change.
3. Use `DLS submitted buy %` / `DLS submitted sell %` to see what the DLS strategy ordered.
4. Use `Filled buy %` / `Filled sell %` and filled shares to see what was actually executed.
5. Use `Base net order %` and `DLS minus Base order %` to understand whether DLS behaved differently from the Base DeepLOB strategy.

Example interpretation:

- If `DLS net order %` is positive and `Base net order %` is zero, the DLS strategy submitted a buy order while the Base model did not.
- If `DLS minus Base order %` is strongly positive, DLS was more aggressive on the buy side than Base DeepLOB.
- If `DLS submitted sell %` is positive but `Filled sell %` is zero, the sell order was submitted but no sell fill appears in the execution audit.
- If `Previous weight` is higher than `DLS predicted target weight`, the optimizer is trying to reduce exposure, so a sell order may appear.
- If `Post-trade weight` and `Final EOD weight` are close to the target, the execution brought the portfolio close to the optimizer’s intended allocation.

## 10. Understanding the two strategies

### Base DeepLOB

The baseline strategy uses the original DeepLOB out-of-sample signal and submitted-order logic. Its daily portfolio path is read directly from:

```text
T001_original_deeplob_exact_daily_log.csv
```

Main base columns used:

| Column              | Meaning                             |
| ------------------- | ----------------------------------- |
| `portfolio_value` | Base portfolio value at end of day. |
| `cash`            | Base cash balance.                  |
| `num_holdings`    | Number of base holdings.            |
| `num_buys`        | Number of base buy orders.          |
| `num_sells`       | Number of base sell orders.         |
| `buy_turnover`    | Base buy notional.                  |
| `sell_turnover`   | Base sell notional.                 |
| `total_costs`     | Base trading costs.                 |

### DeepLOB + DLS

The DLS strategy starts from DeepLOB signals, applies additional filtering, generates target weights, submits orders, records filled trades, and stores end-of-day holdings.

DLS daily equity is reconstructed as:

```text
dls_equity_proxy = eod_market_value / engine_target_gross
```

This is a proxy because the exported DLS files store holdings/trades/weights rather than a single official DLS daily portfolio log.

## 12. Troubleshooting

### App spins forever or becomes slow

Try:

```bash
streamlit cache clear
```

Then restart:

```bash
streamlit run streamlit_app.py
```

Also keep `Enable auto-play module` off until the app fully loads.

### Auto-play does not work

Install:

```bash
pip install streamlit-autorefresh
```

Manual replay controls still work without this package.

### Data not found

Make sure the CSVs are inside:

```text
./data/
```

relative to `streamlit_app.py`.

### Some tables are empty

That usually means the current replay day has no rows in that specific CSV export. Move the replay slider to another day or confirm the relevant CSV exists.

## 13. Important interpretation note

The Base DeepLOB portfolio value is read directly from the base daily log.

The DeepLOB + DLS portfolio value shown in the app is a reconstructed equity proxy:

```text
DLS equity proxy = EOD market value / target gross
```

Therefore, when comparing DLS and Base daily values, interpret the DLS path as a replay-consistent reconstructed path rather than a raw single-column portfolio log.
